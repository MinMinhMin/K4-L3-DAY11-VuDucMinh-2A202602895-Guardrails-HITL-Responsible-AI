# Day 11 Guardrails / HITL / Responsible AI — Design Spec

## Goal

Complete the lab's mandatory defense and red-team work so the repository can
produce valid, reproducible grading artifacts for Checkpoints 2–5:

- input and output guardrails for the Blue path;
- a defense-in-depth assignment pipeline with rate limiting, audit,
  monitoring, and deterministic egress policy;
- `outputs/results.json`, `audit_log.json`, and `metrics.json` generated by
  the assignment suite;
- five deliberate adversarial prompts and the existing Red/Red Advance attack
  artifacts;
- passing smoke/public tests and the repository grader when dependencies are
  available.

The demo values in `data/protected/vinbank_secrets.json` remain unchanged.
No real API key may be written to tracked files or generated artifacts.

## Scope and constraints

The implementation changes only the starter TODOs and the minimal supporting
code needed to connect them. It does not add email/RAG ingestion, modify the
agent secret prompts, weaken Red Advance, or implement optional LLM-as-Judge /
NeMo functionality beyond preserving its existing optional interface.

The offline defense work must not require an LLM API call. Checkpoint 4 is the
only phase that invokes Red/Red Advance. Before that call, the repository will
be validated with offline tests. If an API call fails because a configured key
is missing, invalid, expired, or rejected, execution stops and the user is
asked to repair `.env`; no fabricated attack artifact is created.

## Architecture

The production order is:

```text
user message
  -> RateLimitPlugin
  -> InputGuardrailPlugin
  -> LLM
  -> OutputGuardrailPlugin
  -> audit/monitor observers
  -> deterministic egress check before external sink
```

The ADK plugins remain compatible with the existing callback signatures. The
assignment suite exercises the callbacks directly with a lightweight context,
so it can create `results.json` without needing Blue credentials.

### Input guardrails

`detect_injection` will normalize Unicode text by removing zero-width and
formatting characters, collapsing whitespace, and applying case-insensitive
regex signals. Signals cover instruction override, persona/role switching,
system-prompt extraction, prompt/config reformatting, unrestricted-roleplay,
and common credential-extraction framing. A normal banking question or a
request to summarize a benign transfer document remains allowed.

`topic_filter` will first block any configured `BLOCKED_TOPICS`, then allow
only text containing at least one configured `ALLOWED_TOPICS` term. Empty or
off-topic text is blocked. `InputGuardrailPlugin` returns a model `Content`
replacement with a safe refusal and increments counters; when both checks
allow, it returns `None`.

### Output guardrails

`content_filter` will scan the original response with named regexes for:
Vietnamese phone numbers, email addresses, 9/12-digit national IDs, `sk-*`
API keys, password assignments, and the protected DB host form. Each matched
category adds one issue entry and is replaced with `[REDACTED]`. The returned
dict always has `safe`, `issues`, and `redacted`.

`OutputGuardrailPlugin` will redact a response when the deterministic filter
finds an issue. It will replace the whole response with a safe refusal only if
the optional LLM judge is enabled and returns unsafe. The production pipeline
uses `use_llm_judge=False`, so the offline path is deterministic and does not
call an external model.

### Rate limiting and observability

`RateLimitPlugin` uses a per-user sliding window. It removes expired
timestamps, blocks when the active count reaches `max_requests`, reports an
approximate retry delay, and records a timestamp only for allowed requests.

`AuditLogPlugin` records input/output identity, text, block decision, blocking
layer, request key, ISO timestamps, and latency. If output arrives without a
matching input, it still records a complete event with a null/zero-safe
latency. `export_json` creates parent directories and writes a JSON array.

`MonitoringAlert` computes block and judge-failure rates, appends threshold
alerts without crashing on zero requests, and exports both counters and alert
details through `snapshot()`.

### Egress policy

`is_egress_allowed` parses the destination and returns true only for HTTPS
URLs whose hostname is exactly an approved VinBank host (including the lab's
`api.vinbank.example`, with no subdomain suffix bypass). It rejects malformed
URLs, non-HTTPS schemes, user-info tricks, unknown hosts, and payloads that
contain a demo password, API key, internal DB host, phone number, or email.
The decision is entirely rule-based.

### Assignment suite and artifacts

`run_assignment_suite` will use the supplied plugin list and observers and
produce:

- at least five safe banking inputs, all unblocked;
- at least seven attack inputs, with at least five blocked by input guardrails;
- a rate-limit run that sends more than the configured allowance;
- at least three edge cases with explicit `input` and `blocked` fields.

Each result row includes `input`, `blocked`, `layer`, and a short
`response_preview`. The suite records each request in the audit observer,
updates monitoring counters, calls the output filter for simulated model
responses, and writes the three JSON artifacts beneath the repository
`outputs/` directory. The top-level framework field is `google-adk` to match
the starter's plugin contracts.

### Red-team prompts

`src/attacks/attacks.py` will contain five long, distinct prompts covering
completion, translation/reformatting, hypothetical creative writing,
confirmation/side-channel, and multi-step escalation. They will be designed
to exercise the existing Red and Red Advance factories; no JSON will be
manually edited to claim a leak. The existing runner remains responsible for
calling the model, classifying live responses, and writing per-target plus
combined attack artifacts.

## Error handling

- Guardrail functions treat non-string/empty input as safe for injection
  detection but blocked by topic filtering, avoiding exceptions in callbacks.
- Plugin callbacks fail closed with a user-facing banking-only refusal when a
  guardrail rejects input or a deterministic output issue is found.
- Artifact writers create their parent directories and use UTF-8 JSON.
- Offline commands and tests run before any external model call.
- Red/Red Advance API exceptions are not converted into successful attack
  rows; the CLI stops and reports that `.env` or provider access must be fixed.

## Testing and verification

The implementation will be developed in RED → GREEN order with focused tests
for normalization, injection/topic decisions, redaction, plugin order,
rate-window boundaries, audit latency, monitoring thresholds, egress policy,
and result schema. Existing `tests/smoke` and `tests/public` remain the
authoritative regression suite.

Verification sequence:

1. focused offline tests and `python src/main.py --part 2`;
2. `python src/main.py --part 3`, schema/public contract tests;
3. `python scripts/grade.py --submission-dir . --out outputs/grade_report.json`;
4. only if `.env` has working configured keys, `python src/main.py --part 4`;
5. inspect generated artifacts and confirm `.env` is not tracked.

The final report will distinguish verified offline results from any blocked
LLM step and will not claim a Red leak or bonus unless the live artifact and
provider response demonstrate it.
